# CodeSentinel 产品路线图

本文档用于固化当前产品推进方案，避免后续迭代偏离目标。CodeSentinel 的短期目标不是做一个“会评论代码的玩具”，而是做一款能在 GitHub / GitLab 研发流程中真实落地的 AI 架构审查产品。

## 一、当前阶段：V1.0 可体验 MVP

当前版本已经完成 V1.0 的前端可体验闭环，重点证明产品形态和核心工作流成立。

### 已完成范围

- 接入配置
  - 新项目 / 存量项目初始化路径。
  - `.ai-reviewer.yml` 审查规范预览与编辑。
  - 核心目录、Blocker 规则、测试策略配置。
- 评审工作台
  - 健康度评分。
  - 合并闸口状态。
  - P0 Blocker 列表。
  - 低风险 Checklist。
  - PR 首页自动回复 Markdown 预览。
- 三路审查
  - 拦截层：硬规则风险识别。
  - 意图层：Issue vs Diff 对齐。
  - 架构层：RAG 隐式规范召回。
  - GitHub CI/CD Running 进度流。
- 系统设计
  - Webhook & API。
  - Context Engine。
  - Vector DB。
  - Multi-Agent Router。
  - GitHub / GitLab 平台集成预览。
- 反馈闭环
  - 误报反馈。
  - 漏报补充。
  - 团队策略校准。

### 当前边界

当前版本仍是前端 MVP 和本地规则模拟：

- 未接入真实 GitHub App。
- 未创建真实 GitHub Check Run。
- 未真实回写 PR 评论。
- 未接入真实模型 API。
- 未接入真实向量库。
- 未执行真实沙盒测试。

## 二、下一阶段：工程真实化

下一阶段目标是把“可体验原型”推进成“真实可用 MVP”。优先级如下。

### 1. GitHub App 后端接入

目标：让 CodeSentinel 真正进入 GitHub PR 工作流。

核心任务：

- 创建 GitHub App。
- 监听 `pull_request` Webhook。
- 拉取 PR 元数据、Diff、changed files、Issue、作者、标签和 CI 状态。
- 创建 GitHub Check Run。
- 根据分析状态更新 queued / in_progress / completed。
- 将《变更验收报告》写入 PR 首页评论。
- P0 Blocker 时将 Check Run 标记为 failure，配合 branch protection 拦截合并。

验收标准：

- 用户在 GitHub 发起 PR 后，CodeSentinel 自动开始分析。
- GitHub Checks 中出现 CodeSentinel Review。
- PR 下出现自动生成的验收报告。

### 2. `.ai-reviewer.yml` 真实解析

目标：让仓库配置真正驱动审查策略。

核心任务：

- 从仓库根目录读取 `.ai-reviewer.yml`。
- 支持配置缺失时生成建议配置。
- 用配置驱动：
  - 核心目录。
  - Blocker 规则。
  - 测试策略。
  - 模型路由。
  - RAG 召回范围。

验收标准：

- 修改 `.ai-reviewer.yml` 后，下一次 PR 分析策略发生变化。
- 页面能展示当前生效配置。

### 3. 规则引擎服务化

目标：把当前前端模拟规则迁到后端，形成稳定审查输出。

核心任务：

- 建立统一 Finding 数据结构。
- 支持权限、租户隔离、SQL 拼接、危险 DOM、Prompt 循环、缺少测试等规则。
- 支持规则级置信度、严重级别和证据输出。
- 支持规则启停和阈值配置。

验收标准：

- 后端能独立输入 PR Diff，输出结构化 findings。
- 前端只负责展示，不再承担核心分析逻辑。

### 4. 模型路由接入

目标：用不同模型处理不同任务，在速度、成本和准确性之间取平衡。

核心任务：

- PR 摘要：快速低成本模型。
- Issue 意图对齐：快速模型。
- 架构 RAG 审查：强推理模型。
- 安全漏洞推演：强推理模型，只在 P0/P1 候选风险触发。
- 记录每次调用的延迟、token 成本、失败率和降级策略。

验收标准：

- 每个审查任务能看到模型来源、耗时和成本。
- 模型失败时能降级到规则结果或轻量模型结果。

### 5. RAG 原型

目标：让架构审查不只看当前 Diff，而是理解存量项目上下文。

核心任务：

- 抽取 core / api / service / domain 等核心目录代码切片。
- 解析历史高频修改文件。
- 生成隐式规范。
- 写入向量库。
- PR 分析时按文件路径、调用链和语义相似度召回。

验收标准：

- 架构层输出能引用真实历史文件和规范片段。
- 审查报告能说明“为什么这次改动破坏了既有模式”。

### 6. 反馈持久化

目标：建立团队级审查记忆，持续降低误报和漏报。

核心任务：

- 保存有帮助、太打扰、采纳、忽略、漏报补充等反馈。
- 将反馈按规则、文件路径、模块、作者、模型来源聚类。
- 反向调整置信度阈值、规则权重和 Prompt。
- 高频漏报沉淀为规则或 RAG 样本。

验收标准：

- 团队洞察页能展示真实反馈趋势。
- 同类噪声建议在后续 PR 中主动曝光减少。

## 三、长期方向：AI 原生 Review

以下方向先作为战略储备，不混入 V1.0 工程真实化范围。

### 1. Shift-left to Zero

Review 前置到 IDE 或 Cursor 后台，在代码生成阶段实时拦截架构偏离。目标是让 PR 阶段只剩一句话：“已在开发阶段完成实时拦截与对齐，允许直接合并。”

### 2. 动态破坏性测试

在云端临时环境中运行新分支，自动生成极端业务流量、边界数据和压力测试，用运行证据替代“静态猜测”。

### 3. 状态机 / 知识图谱审查

将系统理解为业务逻辑图，而不是文本文件集合。审查重点从“这行 if/else 是否有问题”升级为“这次修改是否破坏业务状态闭环”。

## 四、推荐执行顺序

建议按以下顺序继续推进：

1. GitHub App 后端接入。
2. `.ai-reviewer.yml` 真实解析。
3. 规则引擎服务化。
4. PR 自动回复和 Check Run 真实回写。
5. 模型路由接入。
6. RAG 原型。
7. 反馈持久化。
8. GitLab 兼容。
9. IDE 实时审查探索。

## 五、阶段判断标准

当以下条件满足时，CodeSentinel 才算从“演示 MVP”进入“真实 MVP”：

- 能被安装到真实 GitHub 仓库。
- 能在 PR 创建后自动触发分析。
- 能在 GitHub Checks 中展示状态。
- 能把验收报告真实写回 PR。
- 能用 `.ai-reviewer.yml` 控制审查策略。
- 至少一部分风险来自后端规则或真实模型，而不是前端模拟。
